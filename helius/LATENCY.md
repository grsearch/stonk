# 买入延迟审查与估算

日期：2026-09-07。按腾讯云美国硅谷新服务器、单连接 Helius WebSocket、SLC Sender 规划。没有目标服务器访问或 Helius key；下列网络与链上范围是工程假设，不是实测、SLA 或统计置信区间。

## 什么叫“买入速度”

1. 砸单执行 → 收到推送：由 Helius 数据路径、网络与本机消息积压决定。当前订阅是 processed，不是预执行流。
2. 收到推送 → 发起买单发送：程序本地逻辑、一次链上批量读取、签名和可靠落盘。
3. 发起发送 → 买单被链上执行：Sender、leader 排序、优先费、tip、拥堵和竞争决定。HTTP 返回签名不是成交。
4. 买单执行 → 程序登记已确认持仓：还要到 confirmed、被每秒轮询观察到，再取得成交回执。

## 逐步骤审查

| 步骤 | 当前实现与影响 |
|---|---|
| WebSocket 接收/解析 | 在 JSON 解析前记录接收时间；单连接、全量匹配交易解析，没有额外等待窗口。高流量时主线程会积压 |
| 本地筛选 | 8 SOL / 10%–30% 跌幅 / 30 SOL 流动性、冷却、去重及持仓检查；不等第二笔卖单，不等 RSI |
| 全钱包锁 | 最显著的吞吐限制：任何在途交易未解决时拒绝新候选；当前不排队。账户关闭等待 finalized，可能占用锁数十秒；未解决异常交易可更久。其他仓位退出也可能被延迟 |
| 6 次/分钟限制 | 用尽直接跳过，不等待下一分钟。因此影响机会覆盖，不会给已准入候选固定增加 10 秒 |
| 准备前持久化与日志 | 同步写文件/落盘会阻塞主线程；20 个持仓和更多去重记录会增大文件。日志量受候选限流约束 |
| 池子读取 | 每次交易读取 8 个账户，一次 getMultipleAccountsInfoAndContext；仍是网络等待，无法宣称零 RPC。minContextSlot 可防止读取早于砸单的状态，也可能因节点落后失败 |
| blockhash | 默认后台每 15 秒刷新。25 秒以上缓存视为过期；已改为与池子读取并行刷新，签名前仍复查有效期 |
| SDK 构建与签名 | 本地执行。已去掉 SDK 已添加的重复 ATA 创建；账户不存在时仍保留一条幂等创建 |
| 发送前持久化 | 签名与交易字节先落盘再发送，保留。否则崩溃恢复时可能对未知买单重复下单 |
| Sender 保活 | 每 5 秒 ping，已修正为消费响应体，帮助连接复用；没有承诺 TCP 永远不会重建 |
| Sender 提交 | 无 preflight、maxRetries=0；1500 ms 超时后以同一份签名字节走 Helius RPC 回退。没有做双路主动抢跑，以免额外请求开销 |
| 确认与回执 | 每秒查 pending 状态，confirmed 后再查完整交易回执，之后才建立持仓和解除锁；轮询相位本身可多等约 0–1 秒，另加请求与节点可见性等待 |
| 已有仓位查询 | 每 15 秒批量查持仓，20 个币为 60 个账户，仍在一次批量调用内。与其他 RPC 共享额度，会产生后台负载 |

RPC 超时目前 10 秒，所以一个卡住的池子读取可能长时间占用准备锁；即使超过 2.5 秒后最终返回，买入仍会在发送前因信号过期被放弃。2.5 秒是入场时效阈值，不是请求会在 2.5 秒自动中断。低费用下未落地的交易可能一直占锁到过期审计完成。程序没有保证“下一笔就跟在砸单后面”。

本次没有移除账户/持仓一致性检查，没有删除发送前落盘，也没有放开不同仓位并行提交。并行执行需要单独设计 WSOL 账户、资金预留和在途状态管理，不能只删除 pending 判断。

## 本机合成数据测速（已执行）

环境：Windows、Node.js v24.19.0，虚拟钱包、合成 cashback 池、无网络、SDK 1.19.0。热身后解析/构建各 200 次；落盘 50 次，状态中包含 20 个模拟持仓、1000 条去重记录和一笔已签名模拟 pending。首次构建签名为 10.707 ms。

| 步骤 | 中位数 | p95 |
|---|---:|---:|
| 一笔小型 ALT 交易 JSON 与事件解析 | 0.336 ms | 0.392 ms |
| SDK 构建、签名、序列化，不含 RPC | 3.141 ms | 3.693 ms |
| 两次可靠状态保存 | 3.745 ms | 5.299 ms |

这些是分项小样本测试，不能当作完整管线 p95，更不能直接代表 Linux 云盘或高负载表现。它未覆盖所有策略检查、日志 I/O、GC、网络和复杂路由交易。Linux 还会 fsync 状态所在目录，云盘可能更慢。

在新服务器上执行 `node helius/scripts/benchmark-local.js` 可复测上述本地部分。该脚本使用随机生成的合成钱包、禁用 RPC，不读取真实私钥下单。`npm run benchmark` 测 Sender ping 和配置 RPC 的 blockhash；ping 也不是完整 getMultipleAccounts 或真实落块耗时。

## 速度预估

假设：没有其他在途交易；健康的同区域网络与节点；连接/blockhash 已热；磁盘没有长尾停顿；费用足以让交易及时被接纳；交易最终成功。

| 区间 | 规划预算，非实测 |
|---|---:|
| 砸单已执行 → Helius 推送到达 | 约 50–300 ms |
| 本地处理、落盘 + 一次批量读取 → 发起发送 | 约 50–250 ms，其中链上读取可按 40–200 ms 预留 |
| 发起发送 → 链上执行 | 可按约 0.3–1.4 秒预留，竞争时可能显著超出 |
| 砸单执行 → 买单执行 | 合计粗估约 0.5–2 秒 |
| 砸单执行 → 程序观察到 confirmed 并登记持仓 | 约 1–4 秒；低频轮询和回执请求使它晚于实际执行 |

这些范围是规划用途，不能据此声称每单达标、零 slot 跟买、一定抢在别人前面或超出范围就是故障。等待锁的信号通常直接漏掉；网络失败、限流、节点落后、Sender 回退和交易未落地时，可能数秒至更久，也可能根本没有成交。

Helius FAQ 给出的 typical land-time 为 ≤1.5 slots，是其服务描述，不是针对这个程序、钱包费率及腾讯云线路的保证。本程序还额外包含推送、RPC 校验、签名及确认观察步骤。

## 上线后看哪些字段

- `stateMs`：状态准备阶段耗时，包含并行时较慢的池子读取/blockhash 刷新。
- `buildSignMs`：状态准备后检查、SDK 构建、签名和序列化耗时。
- `journalMs`：最后一次发送前落盘耗时；不含第一遍准备前落盘。
- `receiveToSendMs`：消息回调收到数据到开始提交，包含 JSON 解析、策略检查及前述准备。
- `senderAckMs`：提交到响应结束；如果走回退，也包括回退等待，并非仅 Sender 网络 RTT。
- `receiveToSubmitMs`：收到消息到提交请求返回，兼容原日志字段。
- `confirmMs`：pending 建立到程序获取确认回执的时间，不是精确落块时间。
- `triggerSlot / landedSlot / slotGap`：买入来源砸单 slot、买单实际 slot 和差值；同 slot 不能证明相邻执行次序。

链上事件 timestamp 是秒级且不代表精确执行时刻，不能用它计算可信的毫秒级全程延迟。需要结合 slot 差和服务端测量才能进一步校准。

官方依据：[Sender FAQ](https://www.helius.dev/docs/faqs/sender)、[Sender 节点与保活说明](https://www.helius.dev/docs/sending-transactions/sender)、[transactionSubscribe](https://www.helius.dev/docs/api-reference/rpc/websocket/transactionsubscribe)。

## 新增反弹观察的开销

观察模块复用解析结果，无额外 RPC 或固定等待。主线程只入队并分批传递数据；特征、模型推断和写盘由独立 worker 执行。没有等待预测结果再买入的步骤。原有发送前交易日志落盘仍保留。

`node helius/scripts/benchmark-shadow.js` 使用本地合成事件测量观察队列：6,400 条、主线程入队及传递摊销 p50 0.0015 ms/条、p95 0.0028 ms/条、无队列丢弃。测量不含完整后台计算、真实行情解析、网络和落块；独立线程也共享 CPU、内存与磁盘，不能据此承诺对主线程零影响。离线训练应放到其他机器或停止交易后运行。

因此仍保留上述 50–250 ms 发送前、0.5–2 秒执行的工程预估，没有提高其可信等级。新增模块尚未在腾讯云实际负载下测量。队列积压会放弃观察样本而不等待，缺失率需要结合 `shadow_health` 监控。模型中默认 500 ms 入场延迟只是可调的标签假设，不是买入测速结果；详见 [反弹观察说明](SHADOW.md)。
